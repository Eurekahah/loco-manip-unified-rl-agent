# （模板）项目文档怎么写

> 用途：本仓库所有"长期维护"的文档（待办、已完成、专题说明）都按这个骨架写，
> 目的是——**只用 2~3 个文档就能看全状态**，历史细节交给 git，不在文档里堆。
>
> 复制本文件开始新文档；`<...>` 是占位符。

---

# <文档标题，例如：总待办清单（TODO）>

**文档职责**：一句话说明这个文档管什么、不管什么。

**维护约定**：

* 每次更新**必须**在"更新记录"里加一行（日期 + 改动摘要 + 相关 commit/分支），
  日期格式 `YYYY-MM-DD`，新纪录加在最上面（时间倒序）。
* 任务条目用 Markdown 复选框：`- [ ]` 未完成 / `- [x]` 已完成；完成的任务**移到
  <DONE 文档>**，并在原处留一行"→ 已迁至 <DONE 文档>（commit）"，不要就地删历史。
* 每条任务写清：**要做什么 / 为什么（依据）/ 怎么验收 / 预估工作量**。
* 文档只写"现在的状态 + 下一步"，过程细节（失败尝试、临时脚本）不要写进来；
  需要留证的实测数据就贴**关键数字 + 复现命令**。
* 涉及具体缺陷/特性的来龙去脉，写到 `<DEFECT_LOG>` 里，本文档只放链接。

## 附：写作细则（写完可以删掉本节）

1. **结论先行**：每个分区第一句就是"现在是什么状态"。
2. **数字要带出处**：写"0.361 → 0.122"时同时写清是哪个 run / 哪个命令得到的。
3. **不要复制代码**：用 `文件:符号名` 指路（行号会漂移），必要时贴 3~5 行。
4. **不要写"待确认"就当完成**：待确认也要进 TODO，并写清确认方法。
5. **旧文档迁移**：如果某个旧文档被本文档取代，在"更新记录"里写明
   "原 `<旧文件名>` 已并入本文档；历史内容见 `<分支> @ <hash>`"。
