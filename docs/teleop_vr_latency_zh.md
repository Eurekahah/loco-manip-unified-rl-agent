# M20 VR 遥操作延迟记录

记录日期：2026-11-10

测试任务：

`Isaac-M20-Piper-Teleop-History-v0`

测试条件：

- 单环境 VR 遥操
- Quest 控制器约 90 Hz，每个数据包包含左右手状态，因此服务端约收到 180 包/秒
- 性能渲染模式
- 当时 `render_interval=8`
- 统计窗口共 16 个采样，每个采样窗口约 2 秒

## 汇总

| 指标 | 结果 |
|---|---:|
| 主循环频率中位数 | 5.0 Hz |
| 主循环周期 | 约 200 ms |
| `env.step` 中位数 | 195.2 ms |
| 服务端收包到控制端消费，p50 | 16 ms |
| 服务端收包到控制端消费，p95 | 约 53 ms |
| 控制命令处理 | 约 1 ms |

## `env.step` 内部分解

以下为每个控制周期内各阶段的平均耗时，来自该次测试的 step breakdown：

| 阶段 | 每周期耗时 | 占 `env.step` 约 |
|---|---:|---:|
| 物理 `sim.step`（4 个子步合计） | 48 ms | 25% |
| `scene.write_data_to_sim` | 48 ms | 25% |
| `scene.update` | 29 ms | 15% |
| `action_manager.apply_action` | 25 ms | 13% |
| GUI 渲染 | 21 ms | 11% |
| 观测等 `compute` | 7.5 ms | 4% |
| 奖励、终止、记录等其余阶段 | 约 17 ms | 9% |

渲染不是主要瓶颈。把渲染频率继续降低不会明显改善控制周期，反而会让第一人称画面出现更大的跨步。

## 端到端延迟估算

### 手柄动作到控制目标生效

1. Quest 浏览器采样并发送：未在本机服务端时间戳中测得。
2. 主机 WebSocket 接收到控制端消费：p50 约 16 ms，p95 约 53 ms。
3. 控制循环等待：周期约 200 ms，平均等待约 100 ms，最坏接近 200 ms。
4. 控制命令处理：约 1 ms。

因此，从手柄动作到机器人开始执行新目标的典型延迟约为 **0.10 到 0.20 秒**。

### 手柄动作到 GUI 看到反馈

新目标生效后，还要等待当前 `env.step` 完成物理和渲染。按 `env.step` 中位数 195 ms 估算：

- 典型视觉闭环约 **0.25 到 0.35 秒**
- 慢尖峰可接近 **0.4 秒**

上述结果不包含 Quest 浏览器到主机的首段网络传输。普通 Wi-Fi 通常再增加约 5 到 20 ms；USB `adb reverse` 通常更低、更稳定。

## 当前瓶颈结论

主要耗时来自仿真环境和动作写入，而不是 WebSocket 或 VR 输入解析：

1. `scene.write_data_to_sim` 约占 25%
2. 物理子步约占 25%
3. `scene.update` 约占 15%
4. action term 执行约占 13%
5. 渲染约占 11%

后续优化应优先检查：

- 高频接触传感器和 `scene.update` 的实际必要性
- `write_data_to_sim` 是否在重复写入未变化的数据
- 低层 tick 中 action term 的计算频率
- 是否可以把遥操阶段的奖励、终止和无关 sensor 更新关闭

## 相机叠加的额外延迟

如果后续把胸前或腕部 RGB 画面传到 Quest：

- 160x120、10 到 15 Hz 的 RGB 采集，仿真端增加通常较小。
- WebRTC/H.264 编码和网络通常再增加约 20 到 50 ms。
- 不建议使用 JSON/Base64 在控制 WebSocket 中传输图像，这会和控制包争抢事件循环和网络带宽。
